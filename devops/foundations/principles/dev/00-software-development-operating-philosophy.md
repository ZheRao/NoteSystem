# Specification-Driven, Experiment-Supported Software Development

> **A personal engineering philosophy and standard operating procedure**  
> Established: 2026-10-11  
> Scope: General-purpose software projects, from small applications to complex platforms  
> Status: Living operating standard; decisions and revisions should be recorded explicitly

## 1. The breakthrough

The central change is to **stop treating code as the starting point of software development**.

A working implementation can exist without its developer having a dependable mental model of the system. Code generated by an AI assistant may be syntactically correct and even functional, yet still be difficult to assess, modify, or trust when its data flow, state transitions, asynchronous behavior, and failure modes are not understood.

A better sequence is:

**Intended behavior → explicit constraints and invariants → necessary knowledge → targeted experiments → architecture → implementation → verification → documented decisions.**

This sequence makes learning purposeful. Rather than studying arbitrary framework features and hoping they will be useful, identify the behavior a project must guarantee, then learn the mechanisms needed to deliver it. Rather than blindly accepting generated code, develop the ability to explain, test, challenge, and maintain it.

The process has two simultaneous outputs:

1. **Product capital:** functioning, reliable, tested, maintainable software.
2. **Knowledge capital:** stronger mental models, reusable patterns, and greater independence on future projects.

Early iterations may require more learning. Later iterations should become faster as proven mechanisms are reused.

## 2. How this philosophy emerged

The motivating experience involved three stages:

1. **Starting from AI-generated CRUD code.** A generated frontend exposed many coupled concepts at once: component boundaries, state ownership, callbacks, controlled inputs, asynchronous operations, and error handling. Reading it line by line did not automatically produce a coherent model of how the application behaved.
2. **Building a small React Task Tracker.** Implementing additions, deletion, editing, busy states, simulated asynchronous APIs, and error handling from first principles made individual mechanisms comprehensible. Small experiments made the consequences of code observable.
3. **Reversing the order.** Instead of building a small project first and discovering what it teaches, begin with the next real product requirement. Determine the unfamiliar concepts needed to satisfy it, then design a deliberately small experiment around those concepts.

The insight is broader than React: **engineering specifications should determine what must be learned; learning should prepare implementation; verification should test the specifications.**

## 3. Governing principles

### 3.1 Develop in bounded increments

Do not attempt to define every screen, workflow, data rule, and invariant for an entire future platform. Establish a broad product direction, then choose the **next bounded, independently valuable objective**. Specify that objective deeply enough to implement and test it. Revisit the plan as the system evolves.

A project roadmap is a sequence of candidate objectives, **not** a commitment to fully designed future features.

### 3.2 Separate *what* from *how*

Start by defining the user-facing purpose and observable guarantees without naming specific hooks, libraries, database tables, or implementation patterns. Technical choices follow the behavioral contract, not the reverse.

A statement such as “the submit button uses `useRef`” is an implementation idea, not a behavioral requirement. “A stale asynchronous response must not replace newer authoritative state” is a behavioral invariant.

### 3.3 Make requirements falsifiable

Avoid vague statements such as “handle errors gracefully.” Specify what the user sees, what data is preserved, what operations are allowed, what is forbidden, and what must remain true after success, failure, retries, cancellation, and concurrent activity.

### 3.4 Learn only what the objective requires

Classify knowledge as **already understood**, **necessary but unfamiliar**, or **interesting but deferrable**. Build experiments for the second category. Do not turn each feature into an unlimited curriculum.

### 3.5 Treat experiments as disposable learning instruments

An experiment should isolate a mechanism, expose its failure mode, and demonstrate why a solution works. It need not resemble the production application. The experiment's success criterion is **demonstrated understanding**, not feature count or polish.

### 3.6 Reuse before reinventing

When a later feature uses already-understood patterns, apply them directly. Only create a new experiment if the requirements introduce a genuinely new uncertainty or reveal a limitation in an existing pattern.

### 3.7 Verify guarantees at the correct boundary

Frontend affordances are not security or data-integrity guarantees. Disabling a button may discourage repeated submissions but cannot by itself prevent duplicate server-side writes. Validation, authorization, uniqueness, idempotency, audit integrity, and concurrency controls must be enforced by the responsible system layer.

### 3.8 Preserve reasoning, not just code

Document current behavior and architecture, but also retain a timestamped record of *why* consequential choices were made and how later decisions superseded them.

### 3.9 Optimize for reliable progress, not perfect foreknowledge

Investigate irreversible or expensive-to-change decisions early. Defer speculative decisions that can be changed safely later. A feature should advance the product while reducing meaningful uncertainty—not require complete understanding of every possible future extension.

## 4. The development cycle

The following phases are logical checkpoints, not a rigid waterfall. Findings can send work back to earlier phases. Small, low-risk changes may combine or skip phases when the corresponding evidence already exists.

### Phase 0 — Choose the next objective

**Question:** What is the smallest coherent piece of product capability worth delivering next?

- State its business/user value and the boundary of the work.
- Identify prerequisites and external dependencies.
- Define what is explicitly out of scope.
- Note major cross-feature risks, especially hard-to-reverse decisions.

**Deliverable:** Short feature brief.

**Exit criterion:** The objective is bounded, valuable, and understandable without designing the whole platform.

### Phase 1 — Define the behavioral contract (no implementation code)

**Question:** What must the system do, allow, prevent, and guarantee?

Capture:

- **Purpose and actors:** who uses it and why.
- **User journeys:** entry points, ordinary flows, and completion states.
- **Operations:** create, read, update, delete, search, filter, navigate, import, export, etc., as applicable.
- **States and transitions:** idle, editing, validating, pending, success, failure, empty, conflict, stale, and disabled where relevant.
- **Invariants:** properties that must remain true across operations.
- **Failure behavior:** errors, timeouts, retries, partial failures, and interrupted work.
- **Concurrency and freshness:** simultaneous actions, duplicate submissions, obsolete responses, and conflicting edits.
- **Trust boundaries:** authorization, validation, rate limits, privacy, abuse prevention, and resource limits.
- **Accessibility and usability:** feedback, keyboard behavior, focus, loading, and recoverability.
- **Acceptance criteria:** concrete observable cases, including negative tests.
- **Assumptions and open questions:** distinguish decisions from unknowns.

**Example:** For a client creation flow, a failed request must not appear successful, entered data should be retained for correction or retry, and invalid inputs must not be accepted by the server. Whether a client can be deleted when referenced elsewhere requires an explicit policy.

**Deliverable:** Feature specification with numbered requirements and invariants.

**Exit criterion:** The most important intended and forbidden behaviors can be tested or reviewed without reading implementation code.

### Phase 2 — Map the knowledge and technical risks

**Question:** What do I need to understand to enforce the contract?

For each important requirement, identify:

- The responsible layer (UI, browser, API, domain service, database, infrastructure).
- Candidate mechanisms and their guarantees.
- Current understanding and evidence.
- Gaps that genuinely block safe implementation.
- Risks that require a proof of concept or early integration test.

Maintain a small matrix:

| Requirement | Responsible layer | Needed concept | Knowledge status | Action |
|---|---|---|---|---|
| Prevent stale display updates | UI/client state | request identity, cleanup, cancellation semantics | Unfamiliar | Targeted experiment |
| Reject unauthorized writes | Backend/API | authentication, authorization, server-side checks | Must validate | Backend test/design |
| Show ordinary form changes | UI | controlled inputs and callbacks | Understood | Reuse pattern |

**Deliverable:** Knowledge map and prioritized risk list.

**Exit criterion:** Required experiments are clearly distinguished from concepts that can be reused or deferred.

### Phase 3 — Design and run targeted experiments

**Question:** Can I reproduce the relevant problem and explain why the chosen mechanism solves it?

For each necessary gap:

1. Formulate a concrete hypothesis.
2. Build the smallest runnable setup that exposes the mechanism.
3. Force normal and adversarial execution sequences.
4. Observe the actual behavior; do not infer success merely from a clean UI.
5. Compare alternatives and their limitations.
6. Explain the result in your own words, including when it would fail.
7. Record the reusable insight and stop.

**Example:** Two simulated requests complete out of order. The older response must not overwrite the newer selection. Test whether request IDs, cleanup, or cancellation prevent the incorrect update, and distinguish ignoring a response from actually aborting a network request.

**Deliverable:** Small experiment, short findings note, and demonstrated understanding.

**Exit criterion:** The mechanism can be explained, reproduced, and tested; remaining limitations are known.

### Phase 4 — Design and implement the real feature

**Question:** How should the production system satisfy the contract with clear responsibilities?

Design only as much architecture as is needed to implement the objective safely:

- Component/module responsibilities and boundaries.
- Ownership of state and data.
- Event, callback, and data flow.
- API contracts and error semantics.
- Persistence, identity, validation, and authorization rules.
- Tests and observability needed to verify guarantees.
- Reuse of existing abstractions; avoid premature generalization.

Implement in small, testable slices. Keep a running link between requirements, implementation, and tests. If implementation reveals a missing requirement, **return to the behavioral contract and revise it explicitly** rather than silently allowing code to define policy.

**Deliverable:** Working implementation with tests and an updated technical design.

**Exit criterion:** The agreed behavior is implemented and observable; the developer can explain the major data and control flows.

### Phase 5 — Verify and obtain independent review

**Question:** Does the system actually satisfy its contract, including adverse cases?

Use a combination of:

- Unit tests for logic and state transitions.
- Integration tests for API/database interactions and enforcement boundaries.
- User-flow tests for critical journeys where appropriate.
- Manual exploration of failure, retry, interruption, accessibility, and concurrency scenarios.
- Independent review (including AI-assisted review) for overlooked edge cases, correctness, security, maintainability, and complexity.

Provide reviewers with the **specification and relevant context**, not only source code. Ask them to identify violated invariants, missing tests, unsafe assumptions, and unjustified complexity. Treat every finding as a hypothesis to evaluate, not an instruction to obey automatically.

**Deliverable:** Verification checklist, review findings, fixes, and residual-risk log.

**Exit criterion:** Critical issues are resolved, acceptance criteria pass, and any accepted risks are explicit.

### Phase 6 — Consolidate documentation and close the increment

**Question:** What should the next developer—or my future self—know?

Update:

- Current feature specification (authoritative behavior).
- Technical design (current architecture and boundaries).
- Tests and run instructions.
- Decision records for consequential choices.
- Open issues and deferred ideas.
- Short retrospective: what was learned, what can be reused, and what to improve in the SOP.

**Deliverable:** A completed, documented increment that can serve as a foundation for the next objective.

**Exit criterion:** Someone can determine how the feature currently behaves, why major decisions were made, and how to verify it.

## 5. Documentation model: current truth plus immutable history

Use **two complementary documentation layers**:

### A. Current-state documents

These describe the system *as it should work now*. They are revised when requirements or implementation change. They should link to relevant decision records.

Examples: feature specifications, architecture overviews, API contracts, test plans, and operational runbooks.

### B. Append-only decision history

An Architecture Decision Record (ADR), or broader Engineering Decision Record (EDR), captures a consequential choice at a particular time. Once accepted, its substantive content should not be silently rewritten. A later change gets a **new record** that references and supersedes the earlier decision. A separate index or current-state document identifies the effective choice.

Record at least:

- Unique ID and date/time (include timezone, preferably ISO 8601).
- Title and status at creation.
- Context and alternatives considered.
- Decision and rationale.
- Consequences, limitations, and tradeoffs.
- Related requirements, tests, and previous decisions.
- Superseding record, if any, referenced from a maintained index.

**Important nuance:** Append-only decision history does **not** mean every specification must be append-only. A permanently accumulating specification becomes hard to read. Keep current specifications concise and authoritative; use decision records and Git history to preserve evolution.

### Suggested repository structure

```text
docs/
  README.md                     # Documentation index
  philosophy/
    development-sop.md          # This operating philosophy
  features/
    client-configuration.md     # Current behavior and acceptance criteria
    audit-log.md
  architecture/
    overview.md                 # Current system architecture
  decisions/
    README.md                   # Decision index and effective statuses
    0001-client-identity.md
    0002-client-deletion.md
    0003-audit-pagination.md
  experiments/
    async-stale-responses.md    # Learning notes and findings
```

Avoid generating a separate document for every trivial choice. Document decisions whose rationale is likely to matter in the future.

### 6.4 Definition of done

```markdown
- [ ] Objective and scope are clear.
- [ ] Critical behavioral requirements and invariants are explicit.
- [ ] Responsibilities are enforced at the correct system boundaries.
- [ ] Required knowledge gaps have been addressed or consciously deferred.
- [ ] Implementation satisfies acceptance criteria.
- [ ] Critical success, failure, and concurrency paths are tested.
- [ ] Independent review findings have been evaluated.
- [ ] No unresolved critical defects remain.
- [ ] Current specification and architecture are accurate.
- [ ] Consequential decisions are recorded with timestamps.
- [ ] Remaining risks and follow-up work are documented.
```

## 7. How to collaborate with AI assistants

Use AI as a **reasoning partner, tutor, challenger, and reviewer**, not an unquestioned source of implementation authority.

A practical collaboration contract:

1. **Specification mode:** Discuss user experience, policy, invariants, and boundaries. Do not generate production code unless requested.
2. **Knowledge-mapping mode:** Explain which concepts are necessary and why. Distinguish language syntax, runtime/platform behavior, framework behavior, and application-specific logic.
3. **Experiment mode:** Prefer hints, questions, execution traces, and minimal demonstrations. Let the developer reason and implement.
4. **Architecture mode:** Compare alternatives against the contract, including failure and maintenance costs.
5. **Implementation mode:** Build in understandable increments. Avoid unexplained abstractions.
6. **Review mode:** Independently challenge the code against the specification; demand reproducible evidence for findings.
7. **Documentation mode:** Record effective behavior and dated decisions without rewriting history.

An AI-generated solution is not accepted merely because it runs or looks elegant. The developer should be able to trace important data flows, explain why safeguards work, and verify the claims through tests.

## 8. Scaling the SOP to different project sizes

| Project type | Appropriate rigor |
|---|---|
| Tiny disposable script | State the goal, key assumptions, and a quick verification; skip formal ADRs. |
| Small personal app | Short feature briefs, focused experiments for new concepts, tests for risky paths, concise notes. |
| Business application | Explicit invariants, API boundaries, authorization, integration tests, and important decision records. |
| High-stakes or complex platform | Stronger threat modeling, data governance, concurrency analysis, observability, migration plans, review gates, and operational documentation. |

The philosophy is constant; the amount of ceremony is proportional to the cost of failure and reversal.

## 9. Common failure modes and countermeasures

| Failure mode | Countermeasure |
|---|---|
| Designing the entire future platform upfront | Specify the next bounded objective; retain only broad roadmap and critical shared constraints. |
| Writing code before agreeing on behavior | Establish observable requirements and invariants first. |
| Endless studying | Tie each experiment to a requirement and a stopping criterion. |
| Recreating the production feature in an experiment | Isolate one mechanism and deliberately trigger its failure mode. |
| Excessive abstractions | Reuse simple proven patterns; generalize only when duplication and variation justify it. |
| Trusting frontend safeguards for server guarantees | Enforce integrity and authorization at authoritative boundaries. |
| Treating AI review as proof | Reproduce findings, test them, and evaluate tradeoffs. |
| Over-documenting trivial decisions | Record consequential choices, not every line of code. |
| Keeping only an append-only specification | Maintain a readable current specification plus append-only decision history. |
| Never finishing a feature | Define acceptance criteria, exit conditions, and a bounded risk budget. |
| Quietly changing policy during implementation | Update the contract explicitly and record material decisions. |

## 10. Illustrative development sequence

For a configuration-heavy application, a sensible sequence might be:

1. **Client configuration:** CRUD, validation, asynchronous feedback, persistence, and identity rules.
2. **Read-only audit history:** navigation/routing, pagination, filtering where justified, and request/abuse limits.
3. **Other metadata configuration:** reuse existing CRUD patterns and document only genuinely new behavior.
4. **Domain input configuration:** references to configured metadata, domain validation, revision semantics, and workflow constraints.
5. **Integration and deployment:** end-to-end data flow, operational reliability, observability, and deployment safeguards.

Each stage receives its **own** bounded contract, knowledge map, experiments if necessary, implementation, verification, and documentation. Future stages can change in light of evidence; they are not fully specified in advance.

## 11. Operating checklist for the start of every feature

Before coding, ask:

1. What concrete capability are we delivering next, and what is out of scope?
2. Who uses it, and what must they be able to do?
3. What must always remain true? What must never happen?
4. What happens on failure, delay, repetition, concurrency, or interruption?
5. Which layer must enforce each guarantee?
6. What do I already understand, and what must I learn?
7. What is the smallest experiment that resolves the important unknown?
8. What architecture is sufficient for this increment without overbuilding?
9. What tests would prove that the implementation meets the contract?
10. What decisions must future maintainers be able to reconstruct?

## 12. Final synthesis

**Do not begin with code. Begin with the behavior worth guaranteeing.**

Specify the next bounded objective. Identify the constraints and invariants that matter. Learn unfamiliar mechanisms through small, intentional experiments. Build the real feature with clear ownership and system boundaries. Verify it against the contract, challenge it through independent review, and preserve both the current design and the history of consequential decisions.

The goal is not to eliminate uncertainty before development. It is to **reduce the right uncertainty at the right time**, accumulate reusable understanding, and steadily deliver software whose behavior can be explained, tested, and trusted.
